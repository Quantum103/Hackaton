# Контракт API: что фронтенд ждёт от бэкенда

Фронт уже ходит на сервер за всеми данными. Этот документ и файл `contract.go` рядом — полный список того, что бэкенд должен отдавать. Структуры в `contract.go` можно скопировать в проект как есть: JSON-имена в них совпадают с тем, что читает фронт.

Образец поведения — `frontend/mock-api.js`. Это браузерная заглушка, которая отвечает на те же запросы в том же формате. Если из описания непонятно, как считать что-то, смотрите одноимённую функцию там. Включается она адресом `?mock=1`, выключается `?mock=0`.

## Общие правила

- **Префикс.** Все маршруты лежат под `/api`. nginx фронта проксирует `/api/…` на бэкенд без изменения пути; адрес бэкенда задаётся переменной `API_UPSTREAM` в `docker-compose.yml`. CORS не нужен: фронт и API на одном адресе.
- **Формат.** Запросы и ответы — JSON в UTF-8.
- **Вход.** Вход и первоначальная настройка возвращают JWT `token`. Во всех защищённых запросах фронт шлёт `Authorization: Bearer <token>`. Backend проверяет подпись, срок действия и активную сессию в БД; нет токена или он недействителен — `401`.
- **Роли.** Читать может любой вошедший. Все изменяющие запросы — только роль `admin`, иначе `403`. Исключения: `POST /auth/logout` и `POST /orders/validate` доступны всем вошедшим. Первый аккаунт при пустой БД становится `admin`; публичная регистрация после этого закрывается. Администратор создаёт остальные учётные записи через `POST /users`, они получают роль `viewer`.
- **Ошибки.** Любой ответ `4xx`/`5xx` — тело `{"message": "…"}`. Текст показывается пользователю как есть, поэтому пишется по-русски.
- **Пустые списки** — `[]`, не `null`. В Go это частая ловушка: неинициализированный срез сериализуется в `null`, и фронт на нём падает.
- **Количества** — целые числа в базовых единицах: граммы (`g`), миллилитры (`ml`), штуки (`pcs`).
- **Время** — RFC 3339 в UTC.
- **Ревизия данных.** В каждом ответе нужен заголовок `X-Data-Rev` с текущим номером ревизии — целым числом, которое растёт при любом изменении данных. По нему страница понимает, что данные изменил кто-то другой, и перезапрашивает их.
- **Часы.** Всё «сейчас» на сервере берётся из одних часов, которые в демо-режиме можно ускорить и перемотать. Сроки, статусы и прогнозы считаются по ним, а не по системному времени.

## Маршруты

### Вход и пользователи

| Метод и путь | Тело запроса | Ответ | Заметки |
|---|---|---|---|
| `GET /auth/setup-status` | — | `200 {setupRequired}` | публично; показывает, нужно ли создать первого администратора |
| `POST /auth/register` | `RegisterRequest` | `200 Session` | только для первоначального создания администратора при пустой БД; далее `403` |
| `POST /users` | `RegisterRequest` | `201 User` | только `admin`; создаёт пользователя с ролью `viewer`; `409` — почта занята |
| `POST /auth/login` | `LoginRequest` | `200 Session` | `401` с одним и тем же текстом для неверной почты и неверного пароля |
| `POST /auth/logout` | — | `204` | |
| `GET /auth/me` | — | `200 User` | фронт сверяет по нему роль каждые три секунды |
| `GET /users` | — | `200 []User` | только `admin` |
| `POST /users/{id}/role` | `SetRoleRequest` | `200 User` | только `admin`; свою роль менять нельзя — `400` |

### Склад и поставки

| Метод и путь | Тело запроса | Ответ | Заметки |
|---|---|---|---|
| `GET /products` | — | `200 []Product` | по алфавиту; для подсказок в формах |
| `GET /stock` | — | `200 []StockItem` | по алфавиту; только продукты, у которых есть партии |
| `GET /stock/{productId}/batches` | — | `200 []Batch` | по возрастанию срока годности |
| `GET /expiry` | — | `200 []ExpiryBatch` | по возрастанию срока; партии с остатком и партии со списанием по сроку |
| `GET /supplies` | — | `200 []Supply` | новые первыми |
| `POST /supplies` | `CreateSupplyRequest` | `201 Supply` | `409` — номер уже есть; вся поставка проверяется до записи |
| `DELETE /supplies/{id}` | — | `204` | удаляет и партии поставки |
| `DELETE /supplies/{id}/items/{productId}` | — | `204` | если позиция была последней — удаляется вся поставка |

### Меню и заказы

| Метод и путь | Тело запроса | Ответ | Заметки |
|---|---|---|---|
| `GET /menu` | — | `200 []Dish` | по алфавиту; с числом порций, стопом и пометкой «горячее» |
| `POST /dishes` | `CreateDishRequest` | `200 Dish` | `409` — такое название уже есть |
| `DELETE /dishes/{id}` | — | `204` | |
| `POST /orders/validate` | `OrderRequest` | `200 ValidateResult` | ничего не списывает; вызывается при каждом изменении корзины |
| `POST /orders` | `OrderRequest` | `200 Order` | при нехватке — `409` с телом `Error`, где заполнен `shortages` |
| `GET /orders` | — | `200 []Order` | новые первыми, включая отклонённые |

### Сроки, уведомления, аналитика

| Метод и путь | Ответ | Заметки |
|---|---|---|
| `GET /alerts` | `200 []Alert` | до 60 последних, новые первыми |
| `GET /pulse` | `200 Pulse` | опрашивается раз в три секунды, должен быть дешёвым |
| `GET /hot-offers` | `200 []HotOffer` | по убыванию приоритета |
| `GET /analytics` | `200 Analytics` | |

### Демо-режим

Все маршруты, кроме `GET /demo/state`, — только `admin`. Каждый возвращает `200 DemoState`.

| Метод и путь | Тело запроса | Что делает |
|---|---|---|
| `GET /demo/state` | — | текущее время и скорость часов сервера |
| `POST /demo/clock` | `ClockRequest` | меняет скорость хода времени |
| `POST /demo/advance` | `AdvanceRequest` | перематывает время вперёд |
| `POST /demo/seed` | — | наполняет склад и меню примером (8 продуктов, 5 блюд) |
| `POST /demo/restock` | — | довозит три продукта с наименьшим остатком |
| `POST /demo/reset` | — | удаляет продукты, поставки, блюда, заказы; аккаунты остаются; часы возвращаются к реальным |

## Правила расчёта

Фронт ничего из этого не считает сам, только показывает. Числа должны сходиться с заглушкой.

1. **Доступный остаток продукта** — сумма остатков по партиям, у которых срок годности ещё не вышел. Это одно определение на всё: стоп-лист, проверку корзины, списание, прогноз.
2. **Заказ** проходит целиком или не проходит вовсе. Потребность складывается по всем блюдам заказа. Списание — с партий с самым ранним сроком (FEFO), в одной транзакции с блокировкой партий. Отклонённый заказ тоже сохраняется в истории.
3. **Стоп-лист** не хранится, а вычисляется: блюдо в стопе, если хотя бы одного ингредиента не хватает на порцию. `stoppedSince` — момент, когда это впервые обнаружено.
4. **Сроки.** Просроченная партия с остатком списывается автоматически: остаток обнуляется, объём записывается в `writtenOff`. При смене статуса партии и при изменении стоп-листа создаётся уведомление. В заглушке это делается на каждом запросе; на сервере — планировщиком, но выборки всё равно должны фильтровать по сроку, не дожидаясь его.
5. **Расход продукта в час** — сумма списаний по заказам за последние 24 часа, делённая на длину окна; окно не длиннее времени с первого движения по продукту и не короче часа.
6. **Объём под риском** партии — сколько останется к концу её срока при текущем расходе, с учётом того, что более ранние партии расходуются первыми.
7. **Приоритет горячего предложения** = срочность × покрытие × эксклюзивность по главному продукту плюс четверть суммы по остальным:
   - срочность = `1 − осталось_часов / окно`, окно = 35 % срока хранения партии, но от 6 до 72 часов;
   - покрытие = доля объёма под риском, которую блюдо способно израсходовать доступными порциями, не больше 1;
   - эксклюзивность = `1 / √(число доступных блюд с этим продуктом)`.
   Блюда с приоритетом ниже 2 из 100 в список не попадают.
8. **Прогноз стоп-листа** — через сколько часов остатка перестанет хватать на порцию: расход идёт с текущим темпом по ранним партиям, партии исчезают в момент истечения срока. Берётся ближайший момент по ингредиентам блюда.
9. **Закупки.** Если расход известен и запаса хватит меньше чем на 48 часов — рекомендовать объём, которого хватит на 72 часа. Если истории продаж нет — рекомендовать, когда запаса меньше чем на 5 порций каждого блюда с этим продуктом, из расчёта на 10 порций.

## Чего пока нет

- **Поток событий.** Сейчас фронт опрашивает `GET /pulse`. Если появится SSE на `GET /events`, опрос заменяется одной функцией в `frontend/shared.js` и `frontend/app.js` — формат событий согласуем отдельно.
- **Параллельные заказы.** Заглушка работает в одном браузере и гонок не проверяет. На сервере два одновременных заказа на последний остаток не должны оба пройти.
