## 1. Технические решения

Бэкенд зафиксирован в первый день. Фронтенд 12.10 переведён с React на чистые HTML, CSS и JS — так изменились требования; ниже описано текущее состояние.

**Бэкенд**
- Go 1.23+, роутер `chi`, PostgreSQL 16, драйвер `pgx/v5`.
- Запросы через `sqlc` (типобезопасный SQL без ORM), миграции — `goose`.
- Контракт API задаёт фронт, бэкенд под него подстраивается (решено 12.10). Он записан в `backend-contract/`: `API.md` — маршруты, коды ответов и правила расчёта, `contract.go` — готовые Go-структуры с JSON-тегами. Образец поведения — `frontend/mock-api.js`.
- Realtime — **SSE**, не WebSocket. Нам нужен только поток сервер → клиент, `EventSource` сам переподключается, прокси настраиваются одной строкой.
- Логи — `slog` в JSON, метрики — `/metrics` для Prometheus (по желанию, Grafana проживёт и на одном Postgres).

**Фронтенд**
- Только HTML, CSS и обычный JS, без сборки и npm. Фреймворк допустим лишь для анимаций и только если без него не обойтись; пока всё сделано на CSS.
- Правило с 12.10: одна страница — один файл. «Поставки», «Заказы», «Стоп-лист» и «Аналитика» уже вынесены в `supplies.html`, `orders.html`, `stoplist.html`, `analytics.html`: разметка, свои стили и скрипт страницы лежат в одном файле. Остальные экраны пока живут в `index.html` + `app.js` и переносятся так же.
- Общее для всех страниц: `styles.css` (дизайн), `api.js` (обмен с сервером), `mock-api.js` (заглушка для разработки), `shared.js` (шапка, проверка входа и роли, форматирование, автообновление, анимации). Библиотека чтения `.xlsx` — в `vendor/`.
- Все данные приходят с сервера: `frontend/api.js` — обычный `fetch` на `/api/…` с токеном в заголовке. nginx фронта проксирует `/api` на бэкенд, адрес — переменная `API_UPSTREAM` в `docker-compose.yml`.

## 2. Модель данных

Самая важная часть: ошибки тут аукнутся во всех трёх главных критериях оценки.

Таблицы БД:

- **`products`** — id, название, единица (`g`/`ml`/`pcs`), типовой срок хранения, минимальный запас. Минимальный запас нужен для рекомендаций закупок, пока нет истории расхода.
- **`supplies`** — id (uuid), номер, дата создания. `id` уникален, поэтому повторная отправка той же поставки не задваивает склад.
- **`batches`** — поставка, продукт, `qty_initial`, `qty_remaining`, `received_at`, `expires_at`, статус. Центральная сущность: одна строка поставки = одна партия.
- **`dishes`, `dish_ingredients`** — меню и техкарты (продукт + количество на порцию). Блюда и их состав заводит пользователь на экране «Меню», сидов нет.
- **`orders`, `order_items`** — заказ и блюда с количеством порций. Отказанные заказы тоже сохраняем со статусом `rejected`.
- **`stock_movements`** — журнал: партия, тип (`receipt`, `order`, `expired`, `manual`), количество, заказ, время. Только дописывается, никогда не правится. Вся аналитика и Grafana строятся по нему.
- **`shortages`** — продукт, блюдо, сколько не хватило, время. Пишется при отказе в заказе, источник статистики дефицита.
- **`stoplist_history`** — блюдо, вошло/вышло, причина (продукт). Нужна для UI («в стопе с 14:20») и аналитики.

Правила, которые закладываем сразу:

1. **Количества — целые числа в базовых единицах** (граммы, миллилитры, штуки). Никаких float: 0.1 + 0.2 сломает проверку «хватает ли».
2. **Время — `timestamptz` в UTC**, срок годности — с точностью до времени, а не до даты. Перевод в локальное — только на фронте.
3. **Единое определение «доступного остатка»**: сумма `qty_remaining` по партиям, где `expires_at > now` и статус активный. Одна SQL-функция/вью, которой пользуются проверка заказа, стоп-лист, горячие предложения и прогноз. Если в разных местах считать по-разному — получим блюдо, которое не в стопе, но не заказывается.
4. **`now` передаётся в запросы параметром из приложения**, а не берётся через SQL `now()`. Причина — в шаге 3.

## 3. Управляемое время (делается в первый день)

Вводим интерфейс `Clock` и пробрасываем его во все сервисы. В проде — реальное время, в тестах — фиксированное, в демо — **ускоренное** (например, ×60: час проходит за минуту).

Зачем так рано: без этого невозможно ни нормально протестировать сроки годности, ни показать жюри за пять минут, как партия проходит путь «свежая → истекает → горячее предложение → списана». Прикручивать задним числом больно — придётся переписывать каждый запрос с `now()`.

## 4. Поставки и склад

**Бэк**
- `POST /supplies` — приёмка: валидация, создание поставки и партий, расчёт `expires_at`, запись `receipt` в журнал. Всё в одной транзакции.
- `GET /supplies`, `GET /supplies/{id}`.
- `GET /stock` — остатки по продуктам (доступно, просрочено, ближайший срок, число партий).
- `GET /stock/{productId}/batches` — партии продукта с остатком и оставшимся временем.

**Фронт**
- Экран «Склад»: таблица продуктов, строка раскрывается в список партий. У партии — полоса оставшегося срока и цветовой статус.
- Экран «Поставки»: список и форма приёмки с динамическими строками продуктов.

**Нюансы**
- Валидация: количество > 0, срок годности в будущем, продукт существует. Неизвестный продукт в поставке — отдельное решение: предлагаю создавать автоматически по `id` + названию, раз кейс говорит, что они приходят в поставке.
- Повтор поставки с тем же `id` → отдаём уже созданную, а не ошибку 500 и не дубль.

## 5. Заказы, FEFO и стоп-лист

Два из пяти критериев оценки живут здесь.

**Алгоритм создания заказа** (одна транзакция):
1. Сложить потребность по всем блюдам заказа в разрезе продуктов. Два блюда с одним ингредиентом — частая ошибка: по отдельности хватает, вместе нет.
2. Заблокировать нужные партии: `SELECT … FOR UPDATE` с сортировкой по `product_id, expires_at, id`. Одинаковый порядок блокировок во всех транзакциях — защита от дедлоков.
3. Проверить, что по каждому продукту доступного остатка хватает. Если нет — откат, запись в `shortages`, ответ `409` со списком: какое блюдо, какой продукт, сколько не хватило.
4. Списать по **FEFO**: идём по партиям от самого раннего срока, одна потребность может размазаться на несколько партий. На каждое списание — строка в журнале.
5. После коммита — пересчёт стоп-листа и события в SSE.

**Стоп-лист**
- Не хранится как ручной флаг, а **вычисляется**: блюдо в стопе, если хотя бы по одному ингредиенту доступного остатка меньше, чем нужно на одну порцию.
- Заодно считаем «сколько порций можно приготовить» = минимум по ингредиентам от `остаток / норма`. Это почти бесплатно и очень полезно в UI.
- Пересчёт запускают три события: поставка, заказ, **истечение срока партии**. Третье — событие времени, а не запрос, поэтому нужен планировщик (шаг 6). Забыть про него — значит блюдо останется доступным с просроченным ингредиентом.
- При изменении состава стоп-листа пишем разницу в `stoplist_history`.

**API**: `POST /orders`, `POST /orders/validate` (проверка корзины без списания), `GET /orders`, `GET /menu` (блюда с флагом стопа, причиной и числом доступных порций), `GET /stoplist`.

**Фронт**
- Экран «Заказы» в виде кассы: карточки блюд, корзина. Блюда в стопе затемнены, с причиной («нет моцареллы»). На карточке — «осталось N порций».
- Корзина на лету дёргает `/orders/validate` и показывает конфликт до нажатия «Оформить».
- Отказ `409` показываем по-человечески: что именно не хватило.

**Обязательный тест**: 50 параллельных заказов на последний остаток — успешных ровно столько, на сколько хватает продукта, остаток не уходит в минус. Это единственный способ убедиться, что блокировки работают.

## 6. Мониторинг сроков и фоновые задачи

**Статусы партии**: `ok` → `warning` → `critical` → `expired`.

Порог нельзя задавать в абсолютных часах: 24 часа для зелени — половина жизни, для крупы — ничто. Считаем по доле оставшегося срока (например, `warning` < 30 %, `critical` < 10 %) с абсолютной подстраховкой снизу. Пороги выносим в конфиг.

**Планировщик** (тик раз в 30–60 секунд по `Clock`):
- находит партии, перешедшие в новый статус, шлёт сигнал в SSE и пишет в ленту уведомлений;
- автоматически списывает просроченные: движение `expired` в журнал, партия закрывается;
- пересчитывает стоп-лист и горячие предложения.

Важно: фильтр `expires_at > now` стоит в самих запросах, планировщик лишь оформляет списание. Корректность не должна зависеть от того, успел ли отработать тик.

**API**: `GET /expiry?status=…`, `GET /alerts`.

**Фронт**: экран «Сроки годности» (партии по срочности), колокольчик с лентой сигналов, всплывающие уведомления по событиям.

## 7. Realtime (SSE)

- `GET /events` — поток событий: `stock.updated`, `stoplist.changed`, `batch.status_changed`, `hot.updated`, `order.created`, `order.rejected`.
- Внутри — простой in-memory hub с подписчиками. Одного инстанса нам хватит, брокер не нужен.
- Событие публикуется **после коммита** транзакции, иначе клиент перезапросит данные и увидит старое.
- На фронте событие не несёт данных, а заставляет открытый экран перезапросить свои. Так проще и нет рассинхрона.
- Heartbeat-комментарий каждые 15–20 секунд и отключённая буферизация на прокси — без этого соединение молча умирает на деплое, хотя локально всё работает.

## 8. Горячие предложения

Отдельный критерий оценки, причём оценивается **качество алгоритма** и объяснение. Логику держим чистой функцией в `domain/` — без БД, на входе срез остатков и техкарты, на выходе ранжированный список с причинами.

**Идея**: рекомендуем блюдо не просто потому, что продукт скоро испортится, а потому что без стимулирования он **не успеет израсходоваться**.

Для каждой партии считаем:
- **Срочность** `U` — растёт к концу срока: `1 − осталось / окно`, где окно зависит от полного срока хранения партии.
- **Объём под риском** `R` — сколько останется к моменту истечения при текущем темпе расхода: `max(0, остаток − темп × осталось_времени)`. Нет истории расхода — берём весь остаток.

Для каждого блюда, которое не в стопе, по каждому «рискованному» ингредиенту:
- **Покрытие** `C` — какую долю `R` блюдо способно утилизировать: `min(1, доступные_порции × норма / R)`. Блюдо с 200 г сливок на порцию полезнее блюда с 10 г.
- **Эксклюзивность** `E` — понижающий коэффициент, если продукт уходит во много других доступных блюд: его и так съедят.

Вклад ингредиента = `U × C × E`; оценка блюда = максимальный вклад + небольшая добавка за остальные ингредиенты (блюдо, спасающее два продукта, выше).

**Объяснение** генерируем из тех же чисел: «Сливки 33 %, партия из поставки №124, истекают через 9 ч. На складе 2,4 л, при текущих продажах останется 1,8 л. 12 порций пасты закроют остаток». Плюс цель: сколько порций и до какого времени продать.

**Нюансы**
- Веса и пороги — в конфиг, не в код: подбирать их придётся на демо-данных.
- Блюда в стопе в список не попадают.
- Табличные тесты с фиксированным временем: «чем ближе срок — тем выше», «больше расход на порцию — выше», «продукт в пяти блюдах — ниже, чем в одном». По сути это спецификация алгоритма, её же можно показать жюри.
- Обновление — по тем же событиям, что и стоп-лист, через SSE.

**API**: `GET /hot-offers`. **Фронт**: блок на дашборде и отдельный экран с карточками, причиной и целью; пометка «горячее» на карточке блюда в кассе.

## 9. Аналитика, прогнозы, рекомендации закупок

Всё считается из `stock_movements`, `shortages` и `stoplist_history` — отдельного хранилища не нужно.

- **Списания**: по дням, по продуктам, доля списанного от поступившего.
- **Дефицитные ингредиенты**: топ по числу отказов и по времени, которое блюда провели в стопе из-за продукта.
- **Прогноз стоп-листа**: для каждого блюда и ингредиента моделируем таймлайн — расход идёт с текущим темпом по FEFO, партии исчезают в момент истечения срока. Момент, когда остатка не хватит на порцию, и есть прогноз. Берём ближайший по ингредиентам: «≈ через 3 ч 20 мин, закончится моцарелла». Мало данных — честно пишем «недостаточно данных», а не рисуем цифру.
- **Предложение поставок** (это базовое требование, не доп): по каждому продукту — на сколько дней хватит запаса с учётом того, что часть испортится раньше, чем будет израсходована. Если меньше целевого — рекомендуем количество. Пока нет истории — сравниваем с минимальным запасом из справочника.

Темп расхода — среднее за скользящее окно по журналу. Окно — в конфиг: при ускоренном времени оно должно масштабироваться.

**Фронт**: экран «Аналитика» с графиками и таблицей «что заказать».

## 10. Генератор событий

Отдельный бинарник `cmd/simulator`, который ходит в API по HTTP, как настоящий внешний клиент. Так заодно получаем нагрузочный и интеграционный тест.

Сценарии:
- **«Обычный день»** — ровный поток заказов, редкие поставки;
- **«Час пик»** — заказы выедают склад, блюда уходят в стоп;
- **«Истекающие продукты»** — приходит поставка с коротким сроком, появляются горячие предложения;
- **«Сброс»** — возврат к стартовому состоянию.

Управление — маленький HTTP-интерфейс симулятора и панель «Демо» в UI: старт/стоп, сценарий, интенсивность, скорость времени.

Нюанс: сброс и ускорение времени на публичном стенде должны быть закрыты хотя бы простым ключом, иначе демо сломает первый любопытный.

## 11. Grafana

- Источник данных — Postgres под **read-only пользователем**, запросы к вьюхам (`v_stock`, `v_writeoffs_daily`, `v_shortages`, …), чтобы не писать тяжёлый SQL прямо в панелях.
- Дашборд и datasource лежат в репозитории (`deploy/grafana/provisioning`) и поднимаются сами. Настроенное руками в интерфейсе потеряется при пересоздании контейнера.
- Панели: остатки по продуктам, партии по статусам срока, списания по дням, заказы и отказы, блюда в стопе во времени, топ дефицитных.
- Анонимный доступ на чтение + ссылка из нашего UI.

## 12. Безопасность и качество

По убыванию важности; нижние пункты — только если есть время.

1. Валидация всех входных данных, единый формат ошибок.
2. Только параметризованные запросы (sqlc это даёт сам).
3. Секреты через переменные окружения, `.env.example` в репо, `.env` в `.gitignore`.
4. CORS по списку доменов, лимит размера тела, rate limit на запись.
5. Идемпотентность: поставки по `id`, заказы по заголовку `Idempotency-Key` (симулятор при ретрае иначе спишет дважды).
6. Регистрация, вход и роли. Ролей две: администратор изменяет данные, остальные только смотрят. Первый зарегистрированный аккаунт — администратор; права другим выдаёт и снимает он на экране «Администрирование». Экраны на фронте готовы; на бэке — хэш пароля, выдача токена, проверка токена и роли на каждом изменяющем запросе (скрытые кнопки на фронте защитой не считаются).

Тесты, без которых нельзя: FEFO, параллельные заказы, скоринг горячих предложений, прогноз стоп-листа, переходы статусов партий по времени.

## 13. Дизайн и UX

«Приятная вёрстка» — отдельный критерий, поэтому тема и токены (цвета статусов, отступы, типографика) настраиваются в первый день, а не в последний.

Экраны: **Главная** (раскрывающаяся панель-дашборд) · **Вход и регистрация** · **Администрирование** · **Склад** · **Поставки** · **Меню** · **Заказы** · **Стоп-лист** · **Горячие предложения** · **Сроки годности** · **Аналитика** · **Демо**.

Дизайн — монохромный, по видео-референсу: слева текст на тёмном градиенте, справа зернистая серая панель, кнопки с прямыми углами. Рабочие экраны и формы выдержаны в нём же.

Что обычно забывают: состояния загрузки, пустые состояния, ошибки сети, индикатор «соединение потеряно» для SSE, адаптив хотя бы под планшет (касса в ресторане — планшет). Цвет статуса дублируем иконкой или подписью.

- Вторник и среда — самые плотные дни. Если к вечеру среды что-то не успеваем — режем в таком порядке: Prometheus-метрики → Grafana (оставляем 2–3 панели) → часть графиков аналитики. Горячие предложения, FEFO и стоп-лист не режем никогда.
